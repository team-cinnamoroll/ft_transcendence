## 2. バックエンド繋ぎ込み後の開発環境について（テストデータの用意）

### 結論

一般的には「**シードデータ（Seed Data）**」と呼ばれる仕組みを使う。今まさにフロントエンドのモックでやっていたことを、今度は**本物のデータベースに対して**行うだけ。つまり「空っぽのDBを本番のように使い始める」のではなく、開発・検証用に**あらかじめサンプルデータをDBに流し込んでおくスクリプト**を用意するのが業界標準のやり方。

### 用語の整理（初学者向け）

| 用語                          | 意味                                                                                                         |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------ |
| マイグレーション（Migration） | テーブルの「箱（構造）」を作る作業。この repo だと `drizzle/` 配下がこれ。                                   |
| シード（Seed）                | その箱に「サンプルの中身（データ）」を入れる作業。マイグレーションとは別の話。                               |
| フィクスチャ（Fixture）       | テストコードの中で「このテストにはこのデータが必要」という単位で用意する少量のデータ。                       |
| Faker（フェイカー）           | それっぽい名前・文章・日付などをランダムに大量生成してくれるライブラリ。手打ちでデータを作る手間を減らせる。 |

### なぜこれで解決するのか

「1年前の投稿を表示する機能」も「検索で他人のシードがヒットする機能」も、**モックが偉いのではなく、モックの中に都合よく用意されたデータが偉い**だけ。なので本番同様のDBを使うようになっても、同じ考え方で「意図的に古い日付の投稿」「意図的に検索語を含む複数ユーザーの投稿」をDBに仕込んでおけば、まったく同じように動作確認できる。やることの本質は変わらず、**データの置き場所がJSファイルの中からPostgreSQLに変わるだけ**。

### このプロジェクトで具体的にどうするか（backendにfaces/seeds等を作るとき）

1. backendに `db:seed`（例）のようなコマンドを用意し、開発環境でだけ実行する（本番環境では絶対に実行しない）
2. 中身は、今の `mocks/faces.ts` / `mocks/seeds.ts` にあるデータをほぼそのまま流用して、バックエンドの本物の作成処理（usecase）経由でDBに入れる
   - モックデータをゼロから作り直す必要がなく、コストがかなり下がる
   - しかも「本物の作成処理を使ってデータを入れる」ことで、その作成処理自体の動作確認にもなる（一石二鳥）
3. 「1年前の投稿」のような日付依存のデータは、**絶対の日付をハードコードしない**で「今日から365日前」のように相対的に計算して生成する
   - もし絶対日付（例: `2025-06-30`）で持ってしまうと、時間が経つとだんだん「1年前」ではなくなっていき、いずれ機能確認ができなくなる。これは意外と見落としがちな落とし穴

### 自動テストはまた別の話

ここまでは「人が目で見て動作確認する開発環境」の話。Vitestなどの**自動テスト**では、DB全体にシードを仕込むのではなく、**そのテストが必要とする最小限のデータだけをテストの中で用意して、終わったら消す**のが基本（この repo でいう `test/` 配下）。「たくさんデータを用意しておく」のはシード、「1テストに1個ずつ必要な分だけ用意する」のはフィクスチャ、と役割が分かれる。

### まとめ

- モック → 本番DB の移行で「スカスカになる」問題は、業界的に**シードデータを用意する**ことで解決するのが標準
- 幸い、このプロジェクトはすでにモックとして良質なサンプルデータを持っているので、それをbackend側のシードスクリプトに転用すればコストは低く抑えられる
- 日付が絡むデータは相対計算で生成するのが定石
- これは今すぐ着手する話ではなく、backendに `faces` / `seeds` 機能を実装するタイミングで一緒に用意すればよいもの（現状は auth/users/presence までしかbackendにないため）
