## フレンドAPI一覧

| #   | メソッド/パス                       | やること                                                  | リクエスト                                        | レスポンス(成功時)                                                                             |
| --- | ----------------------------------- | --------------------------------------------------------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 1   | `POST /requests`                    | フレンド申請を送る                                        | `{ addresseeId }`(相手のユーザーID)               | `201` + 作成された `friendship`(status: `PENDING`)                                             |
| 2   | `PATCH /requests/:requestId/accept` | 届いた申請を承認する                                      | パスに `requestId`                                | `200` + `friendship`(status: `ACCEPTED`)                                                       |
| 3   | `DELETE /requests/:requestId`       | 申請を取り消す(自分が送った側)/拒否する(相手から届いた側) | パスに `requestId`                                | `200` + `friendship`(拒否時は関係自体を削除するので `null` になることもある)                   |
| 4   | `GET /requests?type=incoming        | outgoing`                                                 | 保留中の申請一覧を見る(自分宛て/自分発信を選べる) | クエリ: `type`, `limit`, `cursor`                                                              | `200` + `pendingRequests[]`(申請者のプロフィール込み)、`nextCursor` |
| 5   | `GET /`                             | 承認済みのフレンド一覧を見る                              | クエリ: `limit`, `cursor`                         | `200` + `friendships[]`(相手のプロフィール + **オンライン状態** `isOnline` 込み)、`nextCursor` |
| 6   | `DELETE /:targetUserId`             | フレンド関係を解消する                                    | パスに相手のユーザーID                            | `204 No Content`                                                                               |

## 初学者向けポイント

- **状態は3種類だけ**: `PENDING`(申請中) → `ACCEPTED`(フレンド) / 削除(拒否・解消)。`BLOCKED` も型としては定義済みですが、今回のAPIには専用エンドポイントがなくまだ未使用です
- **ページネーションは「カーソル方式」**: `limit`(1〜100件、デフォルト20件)と `cursor`(前回取得した最後のIDのようなもの)を渡して、続きから取得する形式。ページ番号ではない点に注意
- **一覧系(4, 5)はプロフィール情報も一緒に返ってくる**: 申請一覧・フレンド一覧はユーザーIDだけでなく、相手の `userProfile`(名前・アバターなど)も含めて返るので、フロント側で追加のプロフィール取得は基本不要
- **フレンド一覧だけ「オンライン状態」も付いてくる**: `isOnline` フィールドがあるので、フロントでオンライン表示を作る際はこれをそのまま使えます(別途 presence API を呼ぶ必要はなさそう)
- **エラーハンドリング**: 403(権限なし)、404(申請が見つからない)、409(重複申請などの競合)が代表的。認証は共通で必須(未ログインは401)

## プレゼンス(オンライン状態)API

フレンド一覧の `isOnline` を機能させるための前提API。

| #   | メソッド/パス              | やること                                       | リクエスト              | レスポンス(成功時)                                    |
| --- | -------------------------- | ---------------------------------------------- | ----------------------- | ----------------------------------------------------- |
| 1   | `POST /presence/heartbeat` | オンラインであることを通知する                 | なし(認証情報のみ)      | `200` + `{ success: true }`                           |
| 2   | `POST /presence/offline`   | オフラインであることを通知する                 | なし(認証情報のみ)      | `200` + `{ success: true }`                           |
| 3   | `POST /presence/status`    | 複数ユーザーのオンライン状態をまとめて取得する | `{ userIds: string[] }` | `200` + `{ onlineStatuses: Record<userId, boolean> }` |

### 初学者向けポイント

- **オンライン判定はTTL方式**: `heartbeat` を送るとRedis上のキーが **90秒** だけ有効になる。90秒以内に次の `heartbeat` が来なければ自動的にオフライン扱いになる(明示的な `offline` 呼び出しは無くても勝手にオフラインになる仕組み)
- **フレンド一覧(`GET /`)は内部で `status` 相当の処理を使っている**: フレンド一覧APIのレスポンスに含まれる `isOnline` は、このプレゼンス機能の状態を参照して算出されている。つまり `heartbeat` を送信する仕組みがないと、フレンド一覧の全員が常にオフライン表示になってしまう
- **実装順序の前提**: フレンド機能(特にオンライン表示)を作る前に、アプリ起動中に定期的に `heartbeat` を送り続ける仕組み(ポーリング処理)を用意する必要がある
