# ページ保護 + リフレッシュトークン導線 実装計画

> ゴール: 未ログインのユーザーがアプリ画面(`(app)`配下)を見られないようにし、アクセストークンが切れても裏側で自動的に延長して、ログイン状態を保ち続けられるようにする。あわせて、未ログインユーザー向けの簡単なLP（ランディングページ）をルート（`/`）に用意する。

---

## 1. 背景（なぜ今やるのか）

[AUTH.md](../auth/AUTH.md) の実装当時は、「ページ保護」と「アクセストークンの自動リフレッシュ」はあえて実装しないことになっていた。理由は、`getCurrentUser()` がまだモックの固定ユーザーを返す設計で、「本人確認はできているのに、画面には別人（モック）が表示される」という食い違いが起きるためだった。

その後の対応（#318 で `getCurrentUser().id` が本物のログインIDになったこと等）により、この前提はすでに解消されている。AUTH.md にも「`user-repository` を実データに差し替えてから」「ページ保護を実装するタイミングと同時に」再検討する、と明記されており、今がそのタイミングにあたる。

## 2. 前提知識（初学者向け）

### 2-1. アクセストークンとリフレッシュトークンの役割の違い

| 種類                 | たとえるなら               | 有効期限     | 役割                                                                               |
| -------------------- | -------------------------- | ------------ | ---------------------------------------------------------------------------------- |
| アクセストークン     | 施設内で使う一時的な入館証 | 15分（短い） | 実際にAPIを呼ぶ時に「本人確認済み」の証として使う                                  |
| リフレッシュトークン | 長期の会員証               | 7日（長い）  | 入館証（アクセストークン）が切れた時に、新しい入館証を発行してもらうためだけに使う |

アクセストークンをわざと短命にしているのは、万が一盗まれても被害を15分に抑えるため。その代わり、15分ごとに再ログインさせるのはユーザー体験が悪いので、長持ちするリフレッシュトークンで「裏側でこっそり」新しいアクセストークンを取り直す、という2段構えになっている。

### 2-2. なぜ Server Component ではなく Middleware で実装するのか

Next.js の Server Component（`page.tsx` など）は、Cookie を**読むことはできるが書き込むことはできない**という制約がある。「アクセストークンが切れていたので新しいトークンをCookieに書き込む」という処理は、書き込みが許された場所（Server Actions / Route Handler / **Middleware**）でしかできない。

今回は「どの画面を開いても自動でチェックしてほしい」という性質上、全リクエストの入り口に当たる **Middleware**（`src/proxy.ts`）にこの処理をまとめるのが適している。

### 2-3. ルート（`/`）だけは「リダイレクト」ではなく「出し分け」にする

他の保護対象ページは「未ログインならリダイレクト」で良いが、ルート（`/`）だけは事情が違う。ルートには「未ログインの人向けのLP」と「ログイン済みの人向けのホーム」の**両方**を、同じURLで表示したい。

これは X（旧Twitter）や GitHub など多くのサービスで採用されているパターンで、ブックマークや共有リンクが常に「自分の入り口」として機能するメリットがある（別URL、例えば `/home` に分離する方式は、URLが変わる分あまり一般的ではない）。

実現方法は、Middlewareでリダイレクトさせるのではなく、**`(app)/page.tsx` 自身の中でログイン状態を見て出し分ける**。

```tsx
export default async function Home() {
  const session = await getAuthSession();
  if (!session) {
    return <LandingPage />;
  }
  // ...ここから下は今までのホームの中身（ログイン済み専用）
}
```

このため、Middlewareの「保護対象パス」の判定からはルート（`/`）を除外する（9章参照）。

## 3. 現状（すでにあるもの）

調査の結果、今回必要な部品はほとんどすでに存在しており、「点と点をつなぐ」作業が中心になる。

| 部品                                  | 場所                                                 | 状態                                                                                             |
| ------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Cookie の読み書き                     | `src/lib/session.ts`                                 | 実装済み（`mf_access_token` / `mf_refresh_token`）                                               |
| リフレッシュAPI呼び出し               | `AuthRepositorySpec.refresh`（`auth-repository.ts`） | 実装済みだが、**呼び出しているコードがどこにも無い**（未使用）                                   |
| アクセストークンの検証                | `verifyToken()`（`lib/backend-client.ts`）           | 実装済み（`jose` ライブラリ、Middlewareでも動作するEdge対応のもの）                              |
| ログイン中かどうかの判定              | `getAuthSession()`（`server/usecases/auth.ts`）      | 実装済みだが、**期限切れの場合は自動リフレッシュせず「未ログイン」扱いにする**、と明記されている |
| ページ保護（未ログイン→リダイレクト） | `src/proxy.ts`（Middleware）                         | **未実装**。現状は `next-intl` のロケール振り分けのみ                                            |

## 4. 実装する全体の流れ

```
ブラウザからのリクエスト
        │
        ▼
  src/proxy.ts（Middleware）
        │
        ├─ 1. next-intl でロケールを解決（既存のまま）
        │
        ├─ 2. アクセストークンを検証（verifyToken）
        │       │
        │       ├─ 有効 → そのまま通す
        │       │
        │       └─ 無効／期限切れ
        │             │
        │             ├─ リフレッシュトークンがある
        │             │     │
        │             │     ├─ /auth/refresh を呼んで成功
        │             │     │     → 新しいトークンをCookieに書き込んで通す
        │             │     │
        │             │     └─ 失敗（リフレッシュトークンも無効）
        │             │           → 未ログイン扱いにする
        │             │
        │             └─ リフレッシュトークンも無い → 未ログイン扱いにする
        │
        ├─ 3. 未ログイン かつ 保護対象ページ（(app)配下、ルート / を除く）
        │       → /sign-in へリダイレクト
        │
        ├─ 4. ログイン済み かつ 認証ページ（/sign-in, /sign-up）
        │       → ホーム（/）へリダイレクト
        │
        └─ 5. ルート（/）はリダイレクトさせず、そのまま通す
                → page.tsx 側でログイン状態に応じて LP／ホーム を出し分ける（2-3節参照）
```

## 5. 実装ステップ（小さく分割）

一度に全部やろうとせず、以下の順で確認しながら進める想定。

1. **保護対象パスの一覧を決める**（6章参照）。まずは仕様として合意する。
2. **簡単なLPコンポーネントを作成**し、`(app)/page.tsx` をログイン状態で出し分ける（9章参照）。
3. **Middleware内でアクセストークンを検証する処理を追加**する（まだリフレッシュは実装せず、単に「有効/無効」を判定するだけの段階）。
4. **未ログイン時に保護対象ページ（ルート`/`を除く）へアクセスしたらリダイレクトする処理を追加**する。あわせて、**ログイン済みで `/sign-in` や `/sign-up` に来た場合はホーム（`/`）へリダイレクトする処理**も追加する。ここまでで「ページ保護」は完成する。
5. **アクセストークンが無効だった場合に、リフレッシュトークンで自動的に再発行する処理を追加**する（`AuthRepositorySpec.refresh` を呼ぶ）。
6. **リフレッシュ成功時に、新しいトークンをCookieに書き込む処理を追加**する（ここが「Middlewareでやる意味」の核心部分）。
7. 動作確認（ログイン済み／未ログイン／アクセストークン切れ／リフレッシュトークンも切れ、の4パターン。加えてLPが未ログイン時のルートで正しく表示されるか）。
8. ここまでが完成したら、**8章の後片付け**（`user-directory-repository.ts` への依存の完全廃止）に着手する。

## 6. 保護対象・非保護対象ページ（案）

| 分類               | パス                                                                                              | 未ログイン時                      | ログイン済み時              |
| ------------------ | ------------------------------------------------------------------------------------------------- | --------------------------------- | --------------------------- |
| ルート（出し分け） | `/`                                                                                               | LPを表示（リダイレクトしない）    | ホームを表示                |
| 保護対象           | `(app)/*`（faces, friends, notifications, profile, seeds, settings, subscriptions。ルートを除く） | `/sign-in` へリダイレクト         | そのまま表示                |
| 認証ページ         | `(auth)/sign-in`, `(auth)/sign-up`                                                                | そのまま表示                      | ホーム（`/`）へリダイレクト |
| 非保護対象         | `privacy`, `terms`                                                                                | そのまま表示                      | そのまま表示                |
| 開発用（別途）     | `auth-check`                                                                                      | 現状のまま（本番は404、削除予定） | 現状のまま                  |

## 7. 注意点・確認したいこと

- **Middleware は Edge Runtime で動く**ため、Node.js専用のAPIは使えない。`verifyToken`（jose）や `AuthRepositorySpec.refresh`（fetchベース）は問題なく動く見込みだが、実装時に一度動作確認が必要。
- リフレッシュにも失敗した場合（リフレッシュトークンの期限切れ・失効済みなど）は、Cookieを削除して未ログイン扱いにする必要がある（中途半端に古いCookieが残らないようにする）。
- Middleware は**ほぼ全リクエストで実行される**ため、リフレッシュ処理（バックエンドへの通信）が走るのは「アクセストークンが切れている時だけ」に限定し、無駄なAPI呼び出しを避ける。
- この対応が終わった後、[user-directory-repository.ts](../../src/repositories/user-directory-repository.ts) の「未ログイン時のモックへのフォールバック」は完全廃止する（8章参照）。`subscriptions.ts` / `notifications.ts` はログイン状態による分岐を持たず（常にモック）、今回のスコープには含めない。

## 8. 完了後の後片付け: ログイン状態によるモックへのフォールバックの完全廃止

ページ保護が完成すると、`server/usecases/users.ts` の `getCurrentUser()` / `findUserById()` は「保護されたページの中でしか呼ばれない」＝**呼ばれた時点で必ずログイン済み**という前提が成り立つようになる。そのため、この2関数に残っている「未ログインならモックにフォールバックする」分岐は不要になり、完全に廃止する。

- **`getCurrentUser()`**: `if (!session) return mockUser;` の分岐を削除する
- **`findUserById()`**: `session ? await getUserProfileRepository().getProfileById(...) : null` の三項演算子と、それに伴う `mockUser` へのフォールバックを削除する
- 上記の結果、`getUserDirectoryRepository()` を呼ぶ理由が無くなるため、[user-directory-repository.ts](../../src/repositories/user-directory-repository.ts)（モック実装・Provider）自体も削除する

`getCurrentUser()` には、これとは別に「本物のプロフィール取得に失敗した場合（`realProfile` が null）にモックへフォールバックする」分岐もある。これは「未ログイン」ではなく「ログインはしているがバックエンドAPI呼び出しに失敗した（バックエンド障害など）」場合の話で性質が異なるが、**この分岐も廃止し、モックへのフォールバックはやめる**。

理由: ページ保護を導入する目的は「本人確認と、画面に表示される内容を一致させる」こと（1章参照）。ここでモックにフォールバックしてしまうと、本人確認はできているのに画面には別人（モック）が表示される、というAUTH.mdで元々問題視されていた状態がそのまま再発してしまい、本末転倒になる。

- **`getCurrentUser()`**: `realProfile` が取得できなかった場合、モックを返す代わりに**例外を throw する**。呼び出し元では特別なハンドリングをせず、Next.js の標準的なエラーバウンダリ（`error.tsx`）にそのまま処理を委ね、「情報の取得に失敗しました。再読み込みしてください」といった汎用のエラー画面を表示させる。
- **`findUserById()`**: 「自分自身」を指すケースは `getCurrentUser()` 経由で上記と同じ扱いになる。「他人」のプロフィールが取得できないケースは、存在しない `userId` を指定された場合など正常系でも起こりうるため、こちらは今まで通り `null` を返す（呼び出し元で「見つかりません」表示に使う）。バックエンド障害で取得できないケースと区別できない点は実装時の課題として残るが、本ドキュメントのスコープ外とする。

対象範囲: `subscriptions.ts` / `notifications.ts` はログイン状態による分岐をそもそも持たない（バックエンドAPI自体が未実装で常にモック）ため、この後片付けでは変更しない。

## 9. LP（ランディングページ）の追加

未ログインユーザーのリダイレクト先として、簡単なLPを新規に作成する（2-3節の方針で、ルート `/` に出し分けて表示する）。

### 実装方針

- 新規コンポーネント（例: `components/landing/LandingPage.tsx`）を作成する。中身はサービス名・簡単な説明・ログイン／サインアップへの導線ボタン程度の**簡易な内容**にとどめる。デザインの作り込みは別途。
- `(app)/page.tsx` の先頭で `getAuthSession()` を見て、未ログインなら `<LandingPage />` を返し、ログイン済みなら今までのホームの中身を返すよう分岐する。
- Middleware側では、「保護対象パス」の判定から**ルート（`/`）を除外**する（LPは未ログインでも表示してよいページのため、他の `(app)/*` と同列には扱わない）。

### 注意点

- `(app)/page.tsx` は今後「未ログインでも呼ばれるページ」になる。8章では「`getCurrentUser()` は保護されたページの中でしか呼ばれない」という前提を置いているが、これは**ログイン済み分岐にのみ**当てはまる。LP分岐（未ログイン時）では `getCurrentUser()` などログイン前提の関数を呼ばないように実装する。
- LPの中身（コピー・デザイン）は本ドキュメントでは規定しない。「簡単なもの」であることのみ合意し、詳細は実装時に決める。
